Parte 1 · Diagrama DER: símbolos del modelo E-R

El Diagrama DER es una representacion conceptual de la base de datos: permite identificar entidades, atributos, relaciones y cardinalidades antes de escribir una sola linea de SQL. Caso de ejemplo de toda la guia: una tienda donde los clientes compran productos.

Entidad → rectangulo

Objeto del que queremos guardar informacion. Nombre en MAYUSCULAS: CLIENTE, PRODUCTO, ALUMNO, MATERIA, LIBRO.

Atributo → ovalo

Caracteristica de la entidad, dibujada arriba y conectada con una linea.

Atributo clave → ovalo subrayado

Identifica de forma unica a cada entidad. En la base se convierte en la PRIMARY KEY.

Atributo multivaluado → doble ovalo

Puede tener varios valores para la misma entidad: un cliente con dos telefonos.

Atributo derivado → ovalo punteado

Se calcula a partir de otro dato: la edad sale de la fecha de nacimiento. No se guarda.

Relacion → rombo

Accion o asociacion entre entidades: COMPRA, TIENE, CURSA, PERTENECE, REALIZA...

Cardinalidad → sobre la linea

Cuantas instancias de A se relacionan con cuantas de B: uno a uno, uno a muchos, muchos a muchos.

Cardinalidades y atributos de la relación

La cardinalidad indica cuántas instancias de una entidad pueden relacionarse con cuántas de la otra. Se escribe sobre la línea y se lee desde cada extremo: no es lo mismo 1:N que N:1.

Se lee así: CLIENTE 1 ──── N COMPRA → un cliente realiza MUCHAS compras; cada compra pertenece a UN cliente.
Los tres tipos
CardinalidadEjemploLecturaEn el MER
1 : 1PERSONA – DNI Una persona tiene un solo DNI y un DNI pertenece a una sola persona. Una de las dos tablas lleva la FK (con UNIQUE). No hay intermedia.
1 : NCLIENTE – COMPRA Un cliente realiza muchas compras; cada compra es de un solo cliente. La FK va en la tabla del lado N (compras → cliente_dni).
N : MCLIENTE – PRODUCTO Muchos clientes compran muchos productos. Se crea una tabla intermedia con dos FK. No se resuelve con una sola FK.
Atributos de la relación

Una relación también puede tener atributos propios. En la compra, fecha y cantidad no son del cliente ni del producto por separado: son del hecho de comprar.

-- En el N:M directo el hecho se nombra COMPRA (rombo).
-- Al desdoblarlo, COMPRA pasa a entidad intermedia y fecha y cantidad
-- cuelgan de esa entidad, ya no del rombo. En el MER se escribe en singular;
-- en SQL la tabla se llama compras (plural).
compra
  id_compra      PK
  cliente_dni    FK  -> cliente
  producto_cod   FK  -> producto
  fecha
  cantidad
Regla de oro: si la relación es N:M, se convierte en una entidad intermedia. Sus atributos (fecha, cantidad) se mudan con ella y quedan como columnas de esa tabla.
Error clásico: intentar resolver un N:M con una sola clave foránea. Una compra puede tener varios productos y un producto aparece en varias compras: hace falta la intermedia.
¿La relación tiene datos propios?
SituaciónQué hacer
Relación 1:N sin atributosSolo la FK en el lado N.
Relación 1:N con atributosLos atributos pueden ir en la tabla del lado N, junto a la FK.
Relación N:M (con o sin atributos)Tabla intermedia con dos FK; sus atributos van ahí.

Ejemplo completo de Diagrama DER (vertical)

Cómo se lee el diagrama de la tienda

TramoCardinalidadQué significa
CLIENTE — REALIZA — COMPRA1 : NUn cliente tiene muchas compras; cada compra es de un cliente.
COMPRA — INCLUYE — PRODUCTON : 1Muchas compras incluyen el mismo producto; cada compra incluye un producto.
COMPRA (intermedia)—Guarda las dos FK y sus atributos propios: fecha y cantidad.

El método en 7 pasos

  1. Entidades: ¿de quién o de qué guardo datos? → CLIENTE, PRODUCTO.
  2. Atributos: nombre, id_cliente, precio, nombre del producto.
  3. Claves: lo que identifica cada entidad → id_cliente, código de producto.
  4. Relación: la acción que las une → COMPRA.
  5. Cardinalidad: releé el enunciado → N:M.
  6. Intermedia: si es N:M, insertá COMPRA como entidad.
  7. Atributos del hecho: fecha y cantidad cuelgan de COMPRA, nunca de las entidades.
Fijate en el dibujo: COMPRA aparece como rectángulo (entidad intermedia) y ya no como rombo. Los rombos que quedan son REALIZA e INCLUYE, cada uno con cardinalidad 1:N o N:1.
No confundas: el rombo representa la relación; la entidad intermedia representa la tabla que resuelve un N:M. Al pasar al MER, COMPRA se convierte en la entidad compra (singular); recién en SQL se escribe compras (plural).

Practica guiada: armá tu primer Diagrama DER

Caso - La Pizzería: se registran los clientes (nombre, apellido y uno o más teléfonos) y las pizzas (nombre, precio). Un cliente pide muchas pizzas y una pizza es pedida por muchos clientes. De cada pedido interesan la fecha y la cantidad. Seguí estos pasos:

  1. Buscá las entidades: releé el texto y preguntate ¿de quién / de qué quiero guardar datos? Son cosas: CLIENTE y PIZZA. Dibujá un rectángulo para cada una.
  2. Listá los atributos: colgá de cada entidad un óvalo por característica. Cliente: nombre, apellido, teléfono. Pizza: nombre, precio.
  3. Detectá el multivaluado: ¿algún atributo con varios valores? El teléfono: usale doble óvalo.
  4. Elegí las claves: ¿qué identifica a cada uno? id_cliente e id_pizza: ovalos subrayados.
  5. Nombrá la relación: la acción que une a las entidades es pide: dibujala como rombo. Al releer el texto aparece N:M.
  6. Como es N:M, rompé la relación directa: insertá una ENTIDAD INTERMEDIA llamada PEDIDO entre cliente y pizza.
  7. Los datos del pedido cuelgan de la entidad: fecha y cantidad van como óvalos de PEDIDO, nunca del rombo. Quedan dos relaciones 1:N (cliente-pedido y pedido-pizza).

Parte 2 · Modelo MER: de las ideas a las tablas

El Modelo de Entidades y Relaciones (MER) es el paso que va del dibujo del DER a las tablas reales de MySQL. Acá ya no se dibujan rombos: cada entidad del modelo conceptual se convierte en una caja con columnas, y cada relación se resuelve con una clave foránea o con una tabla intermedia. La convención de esta guía es simple: en el MER se trabaja con entidades en singular (cliente, producto, compra); cuando escribamos SQL, las tablas se llamarán en plural (clientes, productos, compras).

1. Qué cambia entre el DER y el MER

El DER responde «qué cosas hay y cómo se relacionan» con símbolos. El MER responde «cómo se guarda eso en tablas» con columnas, tipos y claves.

En el DER (símbolos)En el MER (tablas)Por qué
Rectángulo = entidadUna caja/tabla con sus columnasLos datos de esa cosa necesitan un lugar donde guardarse.
Óvalo subrayado = clavePK (PRIMARY KEY) con su tipoIdentifica cada fila sin repetirse: es la «dirección» de ese registro.
Rombo = relaciónFK (FOREIGN KEY) o tabla intermediaEn una base relacional las relaciones no se dibujan: se guardan como claves.
Óvalo doble = atributo multivaluadoOtra tabla con FK hacia la originalUna celda no puede tener varios valores; se separan en varias filas.
Óvalo punteado = atributo derivadoNo se guarda: se calcula en la consultaGuardarlo duplicaría datos que ya se pueden obtener.
N:M con atributos propiosTabla intermedia con dos FK y esas columnasLa fecha o la cantidad son del hecho, no de una de las dos entidades.

2. Tipos de atributos: cómo se escribe cada columna

En el MER cada atributo del DER se convierte en una columna con un tipo de dato. Elegir bien el tipo evita desperdiciar espacio y permite hacer comparaciones correctas (por ejemplo, ordenar fechas o sumar importes).

Simple textoVARCHAR(n), donde n es el máximo de caracteres.nombre VARCHAR(50)

Regla práctica: si el dato puede repetirse dentro de una misma fila (varios teléfonos), no va en esa tabla: va en otra con una FK. Si el dato se obtiene multiplicando o sumando otros (un total), no se guarda: se calcula.

3. Cómo se convierte cada símbolo del DER

  • Entidad → tabla. El nombre conceptual va en singular en el MER: cliente. En SQL se escribe clientes.
  • Identificador → PK. Se escribe como primera columna y se marca PK. Si es entero generado por MySQL, también AI.
  • Atributo → columna. Con su tipo elegido según la tabla anterior.
  • Relación → clave ajena. La cardinalidad decide dónde se pone esa FK. Esa es la parte que explicamos ahora.

4. Hacia dónde va la relación (y por qué)

La FK siempre apunta desde la tabla que «mira» a la otra hacia la PK de la otra. Se escribe en la tabla que tiene que recordar quién es el dueño de cada fila. Por eso la dirección depende de la cardinalidad:

  1. 1:N → la FK va en el lado N (la tabla «muchos»). Un cliente tiene muchos pedidos, pero cada pedido es de un solo cliente. Entonces pedido guarda cliente_dni FK apuntando a cliente.dni. Si la pusiéramos en cliente, un cliente tendría que repetir una lista de pedidos en una sola celda, lo cual no es permitido.
  2. 1:1 → la FK va en la tabla que depende de la otra, con UNIQUE. Un alumno tiene una sola libreta y una libreta pertenece a un solo alumno. La libreta guarda id_alumno FK UNIQUE: con UNIQUE evitamos que un alumno tenga dos libretas.
  3. N:M → no hay una sola FK: se crea la entidad intermedia. Muchos clientes compran muchos productos. Ninguna de las dos entidades puede guardar la relación completa en una columna. Por eso nace compra con cliente_dni FK y producto_codigo FK: cada fila es una compra y apunta a las dos PK. Los atributos del hecho (fecha, cantidad) van ahí.
Cómo leer una línea del MER: en 1──N cliente_dni se lee «un cliente aparece en muchas compras y cada compra recuerda a su cliente con cliente_dni». La relación se lee desde el lado N hacia el lado 1, porque es la FK la que apunta a la PK. En este curso escribimos la cardinalidad como 1──N o N──1 al lado del trazo; no hace falta dibujar flecha. Los nombres de entidad van en singular aquí y en plural en el SQL.

Acá está el ejemplo completo. Fijate en la dirección de las FK y en que los nombres de entidad van en singular (en SQL se escribirán en plural):

cliente

  • PK = PRIMARY KEY: identifica cada fila, nunca se repite ni queda vacía.
  • FK = FOREIGN KEY: apunta a la PK de otra tabla y une los datos. Eso se llama integridad referencial: no podés cargar una compra con un cliente que no existe.
  • AI = AUTO_INCREMENT: MySQL numera solo las claves enteras.
  • Multivaluado: el teléfono no va en cliente: va en telefono, con un número por fila y su FK hacia el cliente.
  • Lectura de las líneas: un cliente (1) aparece en N compras; un producto (1) aparece en N compras. Las dos FK están en compra, que es el lado N de ambas relaciones.

Ese MER ya se puede escribir como SQL. El puente entre el dibujo y la base es CREATE TABLE (acá los nombres pasan a plural):

CREATE TABLE compras (
  id_compra        INT PRIMARY KEY AUTO_INCREMENT,
  cliente_dni      VARCHAR(8) NOT NULL,
  producto_codigo  VARCHAR(8) NOT NULL,
  fecha            DATE,
  cantidad         INT,
  FOREIGN KEY (cliente_dni)     REFERENCES clientes(dni),
  FOREIGN KEY (producto_codigo) REFERENCES productos(codigo)
);
¿Con qué símbolo se dibuja la entidad intermedia? En el MER se dibuja con el mismo símbolo que cualquier tabla. No tiene símbolo nuevo: la distinguen sus dos FOREIGN KEY (una hacia cada entidad que unía la N:M original) y sus atributos convertidos en columnas. Suele heredar el nombre que traía del DER: la entidad COMPRA pasa a ser compra en el MER y compras en SQL.

5. Práctica guiada: pasá la pizzería al MER

Usando la pizzería del ejercicio anterior, convertí el diagrama a tablas. Seguí estos pasos:

  1. Cada entidad → una tabla: abrí una caja para cliente y otra para pizza, con sus atributos como columnas y su tipo (sin escribir PEDIDO todavía).
  2. Las claves → PRIMARY KEY: lo que estaba subrayado (id_cliente, id_pizza) ahora se marca como PK.
  3. ¿Cómo era la relación? PIDE era N:M: por eso en el DER insertaste la entidad intermedia PEDIDO; en el MER será la tabla pedido.
  4. Dentro de la intermedia: su PK (id_pedido) y las dos FK (id_cliente apunta a cliente, id_pizza apunta a pizza). Ambas FK van en el lado N, que es el pedido.
  5. Los atributos de la intermedia → columnas: fecha y cantidad colgaban de PEDIDO: ahora son columnas de pedido.
  6. Elegí los tipos de dato: INT para ids y cantidad, VARCHAR para textos, DECIMAL(10,2) para precio, DATE para fecha.
  7. Chequeo final: ¿quedan 3 tablas? ¿cada una tiene PK? ¿las dos FK de pedido apuntan a PK existentes? ¿la cardinalidad está escrita como 1──N y N──1?

Parte 3 · BD: creación y consultas en MySQL

En esta parte primero creamos la base, las tablas y cargamos datos. Después aparecen todos los temas de SELECT, numerados una sola vez. El recorrido termina con la relación entre tablas y las consultas de dos o más tablas.

1. Crear la base de datos

Una base de datos es la carpeta lógica que agrupa las tablas. Se crea una sola vez. IF NOT EXISTS evita un error si ya existe y USE indica con cuál vamos a trabajar:

-- Crea la base (si no existe) y entra en ella
CREATE DATABASE IF NOT EXISTS tiendita;
USE tiendita;

2. Crear tablas

Cada entidad del diagrama se convierte en una tabla. Entre paréntesis se escriben las columnas con nombre, tipo y restricciones, separadas por comas (la última sin coma):

CREATE TABLE clientes (
    dni       VARCHAR(8) PRIMARY KEY,
    nombre    VARCHAR(50) NOT NULL,
    apellido  VARCHAR(50) NOT NULL
);

-- El teléfono es multivaluado: un número por fila, con su FK
CREATE TABLE telefonos (
    id_telefono   INT AUTO_INCREMENT PRIMARY KEY,
    cliente_dni   VARCHAR(8) NOT NULL,
    numero        VARCHAR(20) NOT NULL,
    FOREIGN KEY (cliente_dni) REFERENCES clientes(dni)
);

-- código es texto: así admite valores como 'AB001'
CREATE TABLE productos (
    codigo    VARCHAR(8) PRIMARY KEY,
    nombre    VARCHAR(50) NOT NULL,
    categoria VARCHAR(30),
    precio    DECIMAL(10,2) NOT NULL,
    stock     INT NOT NULL DEFAULT 0
);

-- Tabla intermedia: resuelve la relación N:M cliente-producto
CREATE TABLE compras (
    id_compra        INT AUTO_INCREMENT PRIMARY KEY,
    cliente_dni      VARCHAR(8) NOT NULL,
    producto_codigo  VARCHAR(8) NOT NULL,
    fecha            DATE NOT NULL,
    cantidad         INT NOT NULL,
    FOREIGN KEY (cliente_dni)     REFERENCES clientes(dni),
    FOREIGN KEY (producto_codigo) REFERENCES productos(codigo)
);

3. Insertar datos

INSERT INTO ... VALUES agrega filas. Conviene escribir entre paréntesis los nombres de las columnas: así el orden de los valores queda claro y las columnas AUTO_INCREMENT se omiten. Los textos van entre comillas simples y las fechas como 'AAAA-MM-DD':

INSERT INTO clientes (dni, nombre, apellido) VALUES
    ('30111222', 'Ana',  'Gomez'),
    ('28333444', 'Luis', 'Perez');

-- Un teléfono por fila: Ana tiene dos números
INSERT INTO telefonos (cliente_dni, numero) VALUES
    ('30111222', '2664-111111'),
    ('30111222', '2664-333333'),
    ('28333444', '2664-222222');

INSERT INTO productos (codigo, nombre, categoria, precio, stock) VALUES
    ('AB001', 'Teclado', 'Tecnologia', 8500.00, 10),
    ('AB002', 'Mouse',   'Tecnologia', 4200.50, 15),
    ('AB003', 'Silla',   'Muebles',   12000.00,  4);

INSERT INTO compras (cliente_dni, producto_codigo, fecha, cantidad) VALUES
    ('30111222', 'AB001', '2026-08-20', 2),
    ('30111222', 'AB002', '2026-08-21', 1),
    ('28333444', 'AB001', '2026-08-21', 3);

4. Modificar datos (UPDATE)

UPDATE ... SET ... WHERE ... cambia valores de filas que ya existen. Usá siempre WHERE: sin esa condición se modificarían todas las filas de la tabla.

UPDATE telefonos
SET numero = '2664-999999'
WHERE id_telefono = 1;

-- También se puede calcular sobre el valor actual
UPDATE productos
SET stock = stock + 5
WHERE codigo = 'AB001';

5. Borrar datos (DELETE)

DELETE FROM ... WHERE ... elimina filas. Sin WHERE borra toda la tabla; conviene confirmar primero con un SELECT con la misma condición.

DELETE FROM compras
WHERE id_compra = 3;

-- Vaciar todas las filas de una tabla
TRUNCATE TABLE compras;

6. Agregar, modificar o quitar estructura (ALTER TABLE)

Agregar datos es INSERT (tema 3). Para agregar, cambiar o quitar columnas de una tabla ya creada se usa ALTER TABLE:

ALTER TABLE clientes ADD COLUMN email VARCHAR(80);
ALTER TABLE telefonos MODIFY COLUMN numero VARCHAR(30);
ALTER TABLE clientes DROP COLUMN email;

-- Borrar la tabla completa
DROP TABLE compras;
Resumen: INSERT agrega filas, UPDATE modifica filas, DELETE borra filas y ALTER TABLE cambia la estructura. SELECT solo lee.

7. SELECT: lectura básica y selección de columnas

SELECT lee datos y no modifica la tabla. Es la sentencia más usada.

  • Traer todo: SELECT * FROM clientes; devuelve todas las columnas y filas.
  • Elegir columnas: SELECT nombre, email FROM clientes; trae solo lo pedido.
  • Quitar duplicados: SELECT DISTINCT categoria FROM productos; muestra cada valor una vez.
  • Renombrar con alias: SELECT nombre AS cliente FROM clientes; cambia el nombre de la columna en el resultado.
SELECT DISTINCT categoria AS rubro
FROM productos;

8. Filtrado y ordenamiento

WHERE filtra filas, ORDER BY las ordena y LIMIT recorta la salida.

  • Operadores: =, >, <, >=, <=, <>, LIKE, IN y BETWEEN.
  • Orden: ASC ascendente (por defecto) y DESC descendente.
  • Cantidad: LIMIT es de MySQL/PostgreSQL; en SQL Server se usa TOP.
SELECT nombre, precio
FROM productos
WHERE precio > 1000;

SELECT *
FROM productos
WHERE precio BETWEEN 1000 AND 5000
  AND categoria IN ('Tecnologia', 'Muebles')
ORDER BY precio DESC
LIMIT 10;

-- SQL Server equivalente al LIMIT anterior
-- SELECT TOP 10 * FROM productos ORDER BY precio DESC;
Orden de las cláusulas. Para escribir una consulta se usa: SELECT → FROM → JOIN/ON → WHERE → GROUP BY → HAVING → ORDER BY → LIMIT. El orden lógico en que la base la procesa es FROM/JOIN → WHERE → GROUP BY → HAVING → SELECT → ORDER BY → LIMIT. Por eso WHERE no puede filtrar con un alias creado en SELECT.

9. Cálculos y agrupación de datos

Las funciones de agregación resumen varias filas en un solo valor:

  • COUNT() cuenta filas, SUM() suma, AVG() promedia.
  • MIN() y MAX() devuelven el menor y el mayor valor.
  • GROUP BY arma grupos; HAVING filtra esos grupos ya calculados.
SELECT COUNT(*) AS total_compras,
       SUM(cantidad) AS unidades,
       AVG(cantidad) AS promedio,
       MIN(cantidad) AS menor,
       MAX(cantidad) AS mayor
FROM compras;

SELECT categoria, SUM(stock) AS stock_por_rubro
FROM productos
GROUP BY categoria;

SELECT categoria, COUNT(*) AS cantidad
FROM productos
GROUP BY categoria
HAVING COUNT(*) > 1;

10. Paginación y límites (LIMIT y OFFSET)

  • Primeros N: SELECT * FROM productos LIMIT 5;
  • Saltar filas: LIMIT 10 OFFSET 20 salta 20 y muestra 10; sirve para páginas web.
  • Conviene acompañar siempre con ORDER BY para que la paginación sea estable.
SELECT nombre, precio
FROM productos
ORDER BY codigo
LIMIT 10 OFFSET 20;

-- SQL Server: ORDER BY codigo OFFSET 20 ROWS FETCH NEXT 10 ROWS ONLY

11. Búsqueda de texto y patrones

  • LIKE usa % (cualquier texto) y _ (un carácter). En MySQL la distinción de mayúsculas depende de la collation de la columna; por defecto suele no distinguirlas.
  • REGEXP busca patrones complejos. En MySQL 8 también aparece como REGEXP_LIKE().
  • MATCH() ... AGAINST() es búsqueda de texto completo y necesita un índice FULLTEXT.
SELECT * FROM clientes WHERE nombre LIKE '%garcia%';
SELECT * FROM clientes WHERE nombre LIKE '_ana';

-- codigo es VARCHAR(8), así que puede compararse con un patrón de texto
SELECT * FROM productos
WHERE codigo REGEXP '^[A-Z]{2}[0-9]+$';

-- Requiere: CREATE FULLTEXT INDEX ft_clientes ON clientes (nombre, apellido);
SELECT nombre, apellido
FROM clientes
WHERE MATCH(nombre, apellido) AGAINST ('ana gomez');

12. Manejo de fechas y horas

  • NOW() devuelve fecha y hora actual; CURDATE() solo la fecha. Se puede hacer SELECT sin tabla.
  • YEAR(), MONTH() y DATEDIFF() ayudan a filtrar rangos.
  • DATE_FORMAT() cambia la forma en que se muestra la fecha.
SELECT NOW() AS fecha_hora, CURDATE() AS hoy;

SELECT * FROM compras
WHERE YEAR(fecha) = 2026 AND MONTH(fecha) = 11;

SELECT * FROM compras
WHERE DATEDIFF(CURDATE(), fecha) <= 30;

SELECT DATE_FORMAT(fecha, '%d/%m/%Y') AS fecha_arg
FROM compras;

13. Lógica condicional en los resultados

  • IF() evalúa una condición simple (propio de MySQL).
  • CASE WHEN ... THEN ... ELSE ... END arma categorías con varias condiciones y es más portable.
  • IFNULL() y COALESCE() reemplazan valores NULL por un texto por defecto.
SELECT nombre, IF(stock > 0, 'Disponible', 'Sin stock') AS estado
FROM productos;

SELECT cantidad,
       CASE WHEN cantidad > 2 THEN 'Compra grande'
            ELSE 'Compra chica' END AS tipo
FROM compras;

-- El LEFT JOIN permite ver también clientes sin teléfono cargado
SELECT c.nombre, IFNULL(t.numero, 'Sin teléfono') AS tel
FROM clientes c
LEFT JOIN telefonos t ON t.cliente_dni = c.dni;

SELECT c.nombre, COALESCE(t.numero, 'Sin teléfono') AS tel
FROM clientes c
LEFT JOIN telefonos t ON t.cliente_dni = c.dni;

14. Concatenación y funciones de texto

  • CONCAT() junta textos; CONCAT_WS() usa un separador.
  • GROUP_CONCAT() junta varios valores de un grupo en una sola fila (MySQL).
SELECT CONCAT(nombre, ' ', apellido) AS nombre_completo
FROM clientes;

SELECT CONCAT_WS(' - ', c.nombre, c.apellido, t.numero) AS ficha
FROM clientes c
JOIN telefonos t ON t.cliente_dni = c.dni;

SELECT cliente_dni,
       GROUP_CONCAT(producto_codigo ORDER BY producto_codigo SEPARATOR ', ') AS productos
FROM compras
GROUP BY cliente_dni;

15. Relacionar dos tablas: de PK a FK (explicación y ejemplo)

La PK (Primary Key) identifica cada fila de una tabla. La FK (Foreign Key) es una columna de otra tabla que guarda el valor de esa PK. Así se arma una relación 1:N: un cliente puede tener muchas compras, pero cada compra pertenece a un solo cliente.

clientes.dni  (PK)  ←  compras.cliente_dni  (FK)
productos.codigo (PK) ←  compras.producto_codigo (FK)

En la tabla compras, cliente_dni no es un dato suelto: copia el dni de un cliente existente. La restricción FOREIGN KEY ... REFERENCES impide cargar una compra con un cliente que no existe. Lo mismo pasa con producto_codigo y productos.codigo.

Ejemplo con dos tablas: cruzamos clientes y compras usando c y co como alias de tabla:

SELECT c.nombre, c.apellido, co.fecha, co.cantidad
FROM clientes c
JOIN compras co ON co.cliente_dni = c.dni;

La condición ON co.cliente_dni = c.dni es la que empareja la FK con la PK. Sin ella, la base no sabría qué compra va con qué cliente.

16. Consultas de dos o más tablas

Cuando la información está repartida en varias tablas se usa JOIN. Siempre se apoya en una PK y una FK.

TipoQué devuelve
INNER JOIN (o solo JOIN)Solo filas que coinciden en ambas tablas.
LEFT JOINTodas las filas de la izquierda, aunque no tengan coincidencia a la derecha.
RIGHT JOINTodas las filas de la derecha, aunque no tengan coincidencia a la izquierda.
CROSS JOINCombinación de todas con todas (producto cartesiano).
FULL OUTER JOINNo existe directo en MySQL: se simula con LEFT + RIGHT unidos por UNION.
-- Tres tablas: boleta de compras
SELECT c.apellido, p.nombre AS producto, co.fecha, co.cantidad,
       p.precio * co.cantidad AS total
FROM compras co
JOIN clientes c  ON c.dni    = co.cliente_dni
JOIN productos p ON p.codigo = co.producto_codigo
ORDER BY co.fecha DESC;

-- LEFT JOIN: clientes aunque no hayan comprado
SELECT c.nombre, co.id_compra
FROM clientes c
LEFT JOIN compras co ON co.cliente_dni = c.dni;

-- FULL OUTER simulado en MySQL
SELECT c.nombre, co.id_compra FROM clientes c
LEFT JOIN compras co ON co.cliente_dni = c.dni
UNION
SELECT c.nombre, co.id_compra FROM clientes c
RIGHT JOIN compras co ON co.cliente_dni = c.dni;

Subconsultas. Es un SELECT dentro de otro. Sirve para filtros complejos sin armar la consulta en dos pasos:

SELECT nombre
FROM clientes
WHERE dni IN (
    SELECT cliente_dni FROM compras WHERE cantidad >= 2
);

-- Subconsulta como columna calculada
SELECT c.nombre,
       (SELECT COUNT(*) FROM compras co WHERE co.cliente_dni = c.dni) AS compras
FROM clientes c;

Uniones verticales. UNION y UNION ALL juntan filas de dos consultas con la misma cantidad de columnas y tipos compatibles. UNION elimina duplicados; UNION ALL los conserva:

SELECT nombre AS valor FROM clientes
UNION
SELECT nombre AS valor FROM productos;
Para probar: pegá todo el script en phpMyAdmin o MySQL Workbench. Si insertás una compra con un cliente_dni inexistente, la FOREIGN KEY debe rechazarla: eso confirma que la relación está funcionando.

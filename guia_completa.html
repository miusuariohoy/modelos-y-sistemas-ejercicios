1 MER: el dibujo antes del código

El MER (Modelo Entidad-Relación) es una representación conceptual de la base: muestra qué datos queremos guardar y cómo se relacionan, antes de escribir una sola línea de SQL. El caso que usamos en toda la guía es una tienda: los clientes compran productos.

Las cuatro piezas Entidad     → rectángulo    → CLIENTE, PRODUCTO
Atributo    → óvalo         → nombre, precio
Relación    → rombo         → COMPRA
Cardinalidad → sobre la línea → 1 : N, N : M

Entidad → rectángulo

Objeto del que guardamos datos. Su nombre va en MAYÚSCULAS.

Atributo → óvalo

Característica de la entidad, conectada con una línea.

Atributo clave → subrayado

Identifica de forma única. En la base será la PRIMARY KEY.

Multivaluado → doble óvalo

Puede tener varios valores: un cliente con dos teléfonos.

Derivado → óvalo punteado

Se calcula con otro dato (edad desde la fecha de nacimiento). No se guarda.

Relación → rombo

Acción o asociación: COMPRA, TIENE, CURSA, REALIZA, PRESTA.

Resumen de la simbología
SímboloRepresenta
RectánguloEntidad
RomboRelación
ÓvaloAtributo
Óvalo subrayadoAtributo clave (futura PRIMARY KEY)
Doble óvaloAtributo multivaluado
Óvalo punteadoAtributo derivado
LíneaConecta los elementos
1:1 / 1:N / N:MCardinalidades sobre la línea
Buena práctica: antes de dibujar, releé el enunciado y preguntate “¿de quién o de qué quiero guardar datos?”. Esas son las entidades.
Error clásico: poner los atributos de la compra (fecha, cantidad) dentro de CLIENTE o de PRODUCTO. No son de ninguno de los dos: son del hecho de comprar.

2 Cardinalidades y atributos de la relación

La cardinalidad indica cuántas instancias de una entidad pueden relacionarse con cuántas de la otra. Se escribe sobre la línea y se lee desde cada extremo: no es lo mismo 1:N que N:1.

Se lee así CLIENTE 1 ──── N COMPRA  → un cliente realiza MUCHAS compras;
                               cada compra pertenece a UN cliente.
Los tres tipos
CardinalidadEjemploLecturaEn el DER
1 : 1PERSONA – DNI Una persona tiene un solo DNI y un DNI pertenece a una sola persona. Una de las dos tablas lleva la FK (con UNIQUE). No hay intermedia.
1 : NCLIENTE – COMPRA Un cliente realiza muchas compras; cada compra es de un solo cliente. La FK va en la tabla del lado N (compras → cliente_id).
N : MCLIENTE – PRODUCTO Muchos clientes compran muchos productos. Se crea una tabla intermedia con dos FK. No se resuelve con una sola FK.
Atributos de la relación

Una relación también puede tener atributos propios. En la compra, fecha y cantidad no son del cliente ni del producto por separado: son del hecho de comprar. 

-- En el MER: el rombo COMPRA tiene colgando fecha y cantidad.
-- En el DER: esos atributos pasan a la tabla intermedia compras.
compras
  id_compra    PK
  cliente_id   FK  -> clientes
  producto_id  FK  -> productos
  fecha
  cantidad
Regla de oro: si la relación es N:M, se convierte en una entidad intermedia. Sus atributos (fecha, cantidad) se mudan con ella y quedan como columnas de esa tabla.
Error clásico: intentar resolver un N:M con una sola clave foránea. Una compra puede tener varios productos y un producto aparece en varias compras: hace falta la intermedia.
¿La relación tiene datos propios?
SituaciónQué hacer
Relación 1:N sin atributosSolo la FK en el lado N.
Relación 1:N con atributosLos atributos pueden ir en la tabla del lado N, junto a la FK.
Relación N:M (con o sin atributos)Tabla intermedia con dos FK; sus atributos van ahí.

3 Ejemplo completo: la tienda, paso a paso

Este es el MER que se repite en toda la guía: CLIENTE realiza COMPRA de PRODUCTO. La compra registra fecha y cantidad. Como un cliente compra muchos productos y un producto es comprado por muchos clientes, la relación original es N:M y se resuelve con la entidad intermedia COMPRA.

Cómo se lee el diagrama
TramoCardinalidadQué significa
CLIENTE — REALIZA — COMPRA1 : NUn cliente tiene muchas compras; cada compra es de un cliente.
COMPRA — INCLUYE — PRODUCTON : 1Muchas compras incluyen el mismo producto; cada compra incluye un producto.
COMPRA (intermedia)—Guarda las dos FK y sus atributos propios: fecha y cantidad.
El método en 7 pasos
  1. Entidades: ¿de quién o de qué guardo datos? → CLIENTE, PRODUCTO.
  2. Atributos: nombre, id_cliente, precio, nombre del producto.
  3. Claves: lo que identifica cada entidad → id_cliente, código de producto.
  4. Relación: la acción que las une → COMPRA.
  5. Cardinalidad: releé el enunciado → N:M.
  6. Intermedia: si es N:M, insertá COMPRA como entidad.
  7. Atributos del hecho: fecha y cantidad cuelgan de COMPRA, nunca de las entidades.
Fijate en el dibujo: COMPRA aparece como rectángulo (entidad intermedia) y ya no como rombo. Los rombos que quedan son REALIZA e INCLUYE, cada uno con cardinalidad 1:N o N:1.
No confundas: el rombo representa la relación; la entidad intermedia representa la tabla que resuelve un N:M. Al pasar al DER, COMPRA se convierte en la tabla compras.

4 Del MER al DER: las tablas con PK y FK

El DER (Diagrama Entidad-Relación relacional) es el paso siguiente: cada entidad se convierte en una tabla y cada atributo en una columna con su tipo de dato. Las claves se marcan como PK (Primary Key) y las uniones como FK (Foreign Key). La relación N:M se transforma en una tabla intermedia con dos claves foráneas.

Cada símbolo del MER tiene su traducción
En el MEREn el DER
Entidad (rectángulo)Una tabla (caja con columnas)
Atributo (óvalo)Una columna con su tipo de dato
Atributo clave (subrayado)PRIMARY KEY
Relación 1:NFOREIGN KEY en la tabla del lado N
Relación N:MTabla intermedia con dos FOREIGN KEY
Atributos del romboColumnas extra dentro de la intermedia
Atributo multivaluadoUna tabla propia aparte
Atributo derivadoNo se guarda: se calcula en la consulta
PK, FK y AI
MarcaQué significaEjemplo
PKIdentifica cada fila: no se repite ni queda vacía.clientes.dni
FKApunta a la PK de otra tabla y une los datos.compras.cliente_dni → clientes.dni
AIAUTO_INCREMENT: MySQL numera solo (1, 2, 3…).compras.id_compra
Regla: una tabla intermedia no tiene símbolo nuevo. La reconocés porque tiene dos FK, una hacia cada entidad que unía la N:M, y conserva los atributos del rombo (fecha, cantidad).
Error clásico: poner cliente_dni en productos o al revés. La FK de una N:M va en la intermedia, porque una compra une un cliente con un producto.

5 SQL: crear la base y las tablas en MySQL

El DER se traduce a un script .sql que MySQL ejecuta. Primero se crea la base de datos (la carpeta lógica que agrupa las tablas) y después cada tabla con CREATE TABLE. Entre paréntesis van las columnas: nombre, tipo y restricciones, separadas por comas (la última sin coma).

Paso 1: crear la base y entrar en ella
-- Crea la base (si no existe) y entra en ella
CREATE DATABASE IF NOT EXISTS tiendita;
USE tiendita;

IF NOT EXISTS evita el error si la base ya existe y USE indica a MySQL con cuál vamos a trabajar de ahí en adelante.

Paso 2: crear una tabla
CREATE TABLE clientes (
    dni     INT,              -- columna + tipo
    nombre  VARCHAR(50),      -- texto de hasta 50 caracteres
    precio  DECIMAL(10,2),    -- número con decimales
    fecha   DATE,             -- fecha AAAA-MM-DD
    PRIMARY KEY (dni)        -- restricciones aparte
);
Los tipos de dato más usados
TipoPara qué sirveEjemplo
INTNúmeros enterosdni, stock, cantidad
DECIMAL(10,2)Números con decimales exactosprecio
VARCHAR(n)Texto corto de longitud variablenombre, telefono
DATEFechas AAAA-MM-DDfecha
AUTO_INCREMENTMySQL numera solo (va con INT)id_compra
Restricciones que ya conocés
  • PRIMARY KEY: identifica cada fila, nunca se repite ni queda vacía.
  • NOT NULL: obliga a cargar siempre ese dato.
  • DEFAULT 0: valor que se usa si no se indica otro.
  • FOREIGN KEY ... REFERENCES: conecta la columna con la PK de otra tabla.
Script completo de la base tiendita
-- ==========================================================
-- BASE DE DATOS "TIENDITA"
-- Creada a partir del DER: CLIENTE - COMPRA - PRODUCTO
-- ==========================================================
CREATE DATABASE IF NOT EXISTS tiendita;
USE tiendita;

-- ENTIDAD CLIENTE -> tabla clientes
CREATE TABLE clientes (
    dni INT PRIMARY KEY,
    nombre VARCHAR(50) NOT NULL,
    apellido VARCHAR(50) NOT NULL,
    telefono VARCHAR(20)
);

-- ENTIDAD PRODUCTO -> tabla productos
CREATE TABLE productos (
    codigo INT AUTO_INCREMENT PRIMARY KEY,
    nombre VARCHAR(50) NOT NULL,
    precio DECIMAL(10,2) NOT NULL,
    stock INT NOT NULL DEFAULT 0
);

-- RELACIÓN N:M COMPRA -> tabla intermedia compras
CREATE TABLE compras (
    id_compra INT AUTO_INCREMENT PRIMARY KEY,
    cliente_dni INT NOT NULL,
    producto_codigo INT NOT NULL,
    fecha DATE NOT NULL,
    cantidad INT NOT NULL,
    FOREIGN KEY (cliente_dni)
        REFERENCES clientes(dni),
    FOREIGN KEY (producto_codigo)
        REFERENCES productos(codigo)
);

SELECT c.apellido, p.nombre, co.fecha, co.cantidad,

Prueba extra: intentar insertar una compra con un cliente_dni inexistente debe fallar. La FOREIGN KEY protege los datos y evita compras de clientes que no existen.

6 Consultas JOIN: unir tablas para armar la boleta

Los datos están repartidos en varias tablas: el nombre del cliente en clientes, el precio en productos y la cantidad en compras. JOIN une esas tablas por una condición y devuelve una sola fila combinada. El ON indica qué columna se cruza con cuál. 

SELECT c.apellido, p.nombre, co.fecha, co.cantidad,
       p.precio * co.cantidad AS total
FROM compras co
JOIN clientes  c ON c.dni    = co.cliente_dni
JOIN productos p ON p.codigo = co.producto_codigo;
Qué hace cada línea
ParteQué hace
SELECT ...Elige las columnas que querés ver, incluso una cuenta como precio * cantidad.
AS totalLe pone un nombre a la columna calculada.
FROM compras coTabla base, con el alias co.
JOIN clientes cTrae los datos del cliente de cada compra (alias c).
JOIN productos pTrae el nombre y el precio del producto comprado (alias p).
ON c.dni = co.cliente_dniCondición de unión: la PK de clientes con la FK de compras.
Resultado de la consulta

Cómo pensar un JOIN: seguí el camino de las claves. compras.cliente_dni guarda el DNI; clientes.dni es la PK que lo identifica. Lo mismo pasa con producto_codigo y productos.codigo.
Error clásico: olvidar el ON. Sin condición, MySQL combina todas las filas con todas (producto cartesiano) y la boleta queda con datos que no corresponden.

7 Dibujar el MER y el DER con el programa Dia

Dia es un programa libre y gratuito para hacer diagramas (una alternativa a Visio). Sirve para pasar el MER y el DER a la computadora antes de entregarlos, y para exportarlos como imagen o PDF.

Instalación
  • Windows: bajá el instalador desde www.dia-installer.de (sección Download).
  • Linux: sudo apt install dia.
La pantalla
  • Lienzo central: donde se arma el diagrama.
  • Paleta izquierda: figuras de una colección llamada hoja. El desplegable de arriba cambia de hoja.
  • Hacé clic en una figura y después en el lienzo para colocarla; doble clic para escribir su nombre.
Qué hoja y qué figura usar
Lo que querés dibujarHoja y figura en Dia
Entidad (rectángulo)Hoja ER → Entity
Relación (rombo)Hoja ER → Relationship
Atributo (óvalo)Hoja ER → Attribute
Tablas del DER (PK/FK)Hoja Database → Table + Reference
Trucos que ahorran tiempo
  • Unir figuras: usá la herramienta LÍNEA desde un borde hasta otro; quedan pegadas y siguen unidas al moverlas.
  • Cardinalidades: con la herramienta TEXTO (T) escribí 1:N o N:M junto a la línea.
  • Columnas de una tabla: en la hoja Database, doble clic abre el editor de columnas (nombre, tipo y tilde PRIMARY KEY).
  • Guardar: Archivo > Guardar deja el archivo .dia editable; Archivo > Exportar genera el PNG o PDF para entregar.
  • Atajos: Ctrl+rueda hace zoom, Ctrl+D duplica, Supr borra, Ctrl+Z deshace.
Consejo de entrega: guardá siempre las dos versiones: el .dia para poder corregir y el .png o .pdf para que el docente lo vea sin instalar nada.

    📚 Script 1 · La biblioteca
    
                
    
                    De cada LECTOR se guarda nombre, apellido y uno o varios
                    teléfonos. De cada LIBRO: título, autor y año. Un lector
                    puede llevar muchos libros y un libro puede ser prestado por
                    muchos lectores a lo largo del tiempo. Del préstamo interesan

      2. 
                        
    2. Los teléfonos son multivaluados → tabla lectores_telefonos.
      3. 
                        
    3. Las fechas del préstamo son atributos del rombo: van en prestamos.
      4.

    🐾 Script 2 · La veterinaria
    
                
    
                    De cada DUEÑO: nombre, fecha_nacimiento
                    y varios teléfonos (multivaluado). La EDAD no se
                    guarda: se calcula (derivado). De cada MASCOTA: nombre y especie.
                    Un dueño puede tener muchas mascotas, pero cada mascota pertenece
                    a un solo dueño (relación 1:N).
                
    
                
    
                    Pista: pensá dónde va la FK
                    
      
                        
    1. Al ser 1:N, la FK id_dueno va en mascotas (lado N).
      2. 
                        
    2. No hace falta tabla intermedia.
      3. 
                        
    3. La edad se calcula con TIMESTAMPDIFF(YEAR, ...) en el SELECT.
      4.

    CREATE DATABASE IF NOT EXISTS veterinaria;

CREATE TABLE duenos (

CREATE TABLE duenos_telefonos (
    id_telefono INT AUTO_INCREMENT PRIMARY KEY,

);

-- RELACIÓN 1:N -> FOREIGN KEY en la tabla del lado N
CREATE TABLE mascotas (
    id_mascota INT AUTO_INCREMENT PRIMARY KEY,
    nombre VARCHAR(40) NOT NULL,
    especie VARCHAR(30) NOT NULL,
    id_dueno INT NOT NULL,
    FOREIGN KEY (id_dueno)
        REFERENCES duenos(id_dueno)

    🎓 Script 3 · La escuela (boletín)
    
                
    
                    De cada ALUMNO: dni (clave), nombre y apellido. De cada
                    MATERIA: id y nombre. Un alumno cursa muchas materias
                    y una materia la cursan muchos alumnos. De cada cursada se guardan
                    nota_1co y nota_2co; el
                    promedio se calcula. Es el espejo de la base
                    bdescuela del proyecto Boletín Digital.
                
    
                
    
                    Pista: relación N:M con notas
                    
      
                        
    1. CURSA es N:M → tabla intermedia cursadas.
      2. 
                        
    2. nota_1co y nota_2co son atributos del rombo: columnas de cursadas.
      3. 
                        
    3. El promedio es derivado: (nota_1co + nota_2co) / 2 AS promedio.
      4. 
                    
    
                
    
                
                
    
                    
                    
                
    
                
    
                
    
                    Ver la solución del anexo (escuela_der.sql)
                    
    CREATE DATABASE IF NOT EXISTS escuela_der;
USE escuela_der;

CREATE TABLE alumnos (
    dni INT PRIMARY KEY,
    nombre VARCHAR(50) NOT NULL,
    apellido VARCHAR(50) NOT NULL
);

CREATE TABLE materias (
    id_materia INT AUTO_INCREMENT PRIMARY KEY,
    nombre VARCHAR(50) NOT NULL
);

-- RELACIÓN N:M CURSA -> tabla intermedia
CREATE TABLE cursadas (
    id_cursada INT AUTO_INCREMENT PRIMARY KEY,
    alumno_dni INT NOT NULL,
    materia_id INT NOT NULL,
    nota_1co DECIMAL(4,2),
    nota_2co DECIMAL(4,2),
    FOREIGN KEY (alumno_dni)
        REFERENCES alumnos(dni),
    FOREIGN KEY (materia_id)
        REFERENCES materias(id_materia)
);

    (28333444, 'Luis', 'Perez');

-- El PROMEDIO es DERIVADO: se calcula en la consulta
SELECT a.apellido, m.nombre,
       c.nota_1co, c.nota_2co,
       (c.nota_1co + c.nota_2co) / 2 AS promedio
FROM cursadas c
JOIN alumnos  a ON a.dni        = c.alumno_dni
JOIN materias m ON m.id_materia = c.materia_id;
    
                
    
            
    

            
    
                
    🏋️ Script 4 · El gimnasio
    
                
    
                    De cada SOCIO: número de socio (clave), nombre, apellido y uno
                    o varios teléfonos. De cada ACTIVIDAD: código,
                    nombre, horario y cupo. De cada ENTRENADOR: legajo (clave),
                    nombre y especialidad. Un socio se inscribe en muchas actividades
                    y una actividad tiene muchos socios; de cada inscripción se
                    guardan fecha_alta y turno.
                    Cada actividad tiene un solo entrenador a cargo, y un entrenador
                    puede estar a cargo de muchas actividades.
                
    
                
                
    
                    
                    
                
    
                
    
                
    
                    Ver la solución del anexo (gimnasio.sql)
                    
    CREATE DATABASE IF NOT EXISTS gimnasio;
USE gimnasio;

CREATE TABLE socios (
    nro_socio INT PRIMARY KEY,
    nombre VARCHAR(50) NOT NULL,
    apellido VARCHAR(50) NOT NULL
);

-- ATRIBUTO MULTIVALUADO -> tabla propia
CREATE TABLE socios_telefonos (
    id_telefono INT AUTO_INCREMENT PRIMARY KEY,
    nro_socio INT NOT NULL,
    telefono VARCHAR(20) NOT NULL,
    FOREIGN KEY (nro_socio)
        REFERENCES socios(nro_socio)
);

CREATE TABLE entrenadores (
    legajo INT PRIMARY KEY,
    nombre VARCHAR(60) NOT NULL,
    especialidad VARCHAR(50) NOT NULL
);

-- RELACIÓN 1:N -> FOREIGN KEY en la tabla del lado N
CREATE TABLE actividades (
    cod_actividad INT AUTO_INCREMENT PRIMARY KEY,
    nombre VARCHAR(50) NOT NULL,
    horario VARCHAR(40) NOT NULL,
    cupo INT NOT NULL,
    legajo_entrenador INT NOT NULL,
    FOREIGN KEY (legajo_entrenador)
        REFERENCES entrenadores(legajo)
);

-- RELACIÓN N:M SOCIO-ACTIVIDAD -> tabla intermedia
CREATE TABLE inscripciones (
    id_inscripcion INT AUTO_INCREMENT PRIMARY KEY,
    nro_socio INT NOT NULL,
    cod_actividad INT NOT NULL,
    fecha_alta DATE NOT NULL,
    turno VARCHAR(20) NOT NULL,
    FOREIGN KEY (nro_socio)
        REFERENCES socios(nro_socio),
    FOREIGN KEY (cod_actividad)
        REFERENCES actividades(cod_actividad)
);
